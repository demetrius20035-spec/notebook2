## 1. Общие сведения

### 1.1. Назначение системы

RepairExpert AI — это десктопное приложение, представляющее собой интегрированную экспертную систему для сервисного центра по компонентному ремонту электроники. Система объединяет CRM, ERP-модуль, базу знаний с RAG-поиском, экспертную диагностику на основе LLM и полный цикл документооборота в единой платформе.

Система ориентирована на мастерские и сервисные центры, занимающиеся компонентным ремонтом:
- блоков питания (ATX, импульсные, зарядные устройства);
- материнских плат ПК и ноутбуков;
- ноутбуков (цепи питания, VRM, мультиконтроллеры, BGA-узлы);
- планшетов и смартфонов (PMIC, зарядные цепи, интерфейсы);
- другой электроники.

### 1.2. Цели проекта

- Сократить время диагностики за счёт структурированного журнала ремонта и ИИ-подсказок.
- Накопить и эффективно использовать базу знаний мастерской (ремонты, даташиты, форумные решения).
- Автоматизировать полный цикл документооборота (приёмка, дефектовка, счета, акты, гарантия).
- Обеспечить учёт клиентов, устройств, компонентов и склада.
- Работать стабильно в оффлайн-режиме; LLM-интеграция — опциональный слой поверх рабочей системы.
- Масштабироваться от одного мастера до небольшого сервисного центра (до 10 рабочих мест).

### 1.3. Аудитория и пользователи

| Роль          | Описание                                                        |
|---------------|-----------------------------------------------------------------|
| Администратор | Полный доступ, управление пользователями, настройки системы     |
| Инженер       | Ведение ремонтов, компонентная база, база знаний                |
| Приёмщик      | Приёмка/выдача, клиенты, печать документов                      |
| Кладовщик     | Склад компонентов, приходные/расходные операции                 |
| Бухгалтер     | Финансовые отчёты, просмотр без редактирования                  |

## 2. Функциональные требования

### 2.1. Модуль CRM — Управление клиентами

**Карточка клиента:**
- ФИО, телефон (уникальный), e-mail, адрес, произвольные заметки.
- Флаг «чёрный список» с причиной.
- Автоматическая классификация: VIP (≥10 ремонтов), постоянный (≥3), новый.
- История всех ремонтов, история платежей и предоплат.
- Счётчик задолженностей.

**Поиск клиентов:**
- По ФИО, телефону, e-mail.
- По истории устройств (серийный номер, IMEI).

---

### 2.2. Модуль приёмки оборудования

**Карточка устройства:**
- Тип устройства (ноутбук, смартфон, планшет, материнская плата, блок питания, монитор, другое).
- Производитель, модель, год выпуска, серийный номер, IMEI.
- Платформа / ревизия платы (например, NM-D221, LA-B181P).
- Пароль от устройства (шифруется в БД).
- Состояние при приёмке: текстовое описание + фотографии (минимум 4 ракурса).
- Признаки: следы залития, механические повреждения, следы предыдущего ремонта.

**Ремонтная заявка (тикет):**
- Автоматически генерируемый номер: `РМ-ГГГГ-NNNNN`.
- Привязка к клиенту и устройству.
- Описание проблемы со слов клиента.
- Приоритет: обычный / высокий / срочный.
- Назначение ответственного инженера.
- Статусы: Принят → Диагностика → В работе → Ожидание деталей → Ожидание клиента → Готов → Выдан → Закрыт → Гарантийный случай.

**Печать при приёмке:**
- Квитанция о приёмке (с QR-кодом тикета).
- Акт приёмки-передачи (2 экземпляра).
- Дефектовочная ведомость.

---

### 2.3. Модуль ведения ремонта

**Журнал ремонта (Repair Session Log):**

Каждое действие инженера фиксируется как отдельная запись:
- Метка времени.
- Тип действия: измерение / замена компонента / заметка / запрос к AI / фото / пайка / прошивка / тест.
- Описание.
- Опциональное вложение (фото, осциллограмма, дамп BIOS).

Примерный вид журнала:
```
10:01  [ПРИНЯТ]       Ноутбук Lenovo ThinkPad T14 Gen2
10:05  [ИЗМЕРЕНИЕ]    VIN = 19.4 В — OK
10:07  [ИЗМЕРЕНИЕ]    +3VALW = 3.3 В — OK
10:09  [ИЗМЕРЕНИЕ]    +5VALW = 0 В — FAIL
10:12  [AI]           Вероятность: TPS51225 — 62%, EN отсутствует — 25%
10:18  [ФОТО]         Фото платы в зоне U301 (прикреплено)
10:25  [ЗАМЕНА]       TPS51225C → TPS51225B (аналог)
10:40  [ТЕСТ]         Ноутбук запустился, все напряжения в норме
```

**Карта измерений:**

Структурированная таблица напряжений — не свободный текст:

| Линия   | Норма  | Измерено | Статус |
|---------|--------|----------|--------|
| VIN     | 19.0 В | 19.4 В   | ✔      |
| +3VALW  | 3.3 В  | 3.3 В    | ✔      |
| +5VALW  | 5.0 В  | 0.0 В    | ✖      |

Хранить всю историю изменений измерений (до и после ремонта).

**Компоненты в ремонте:**
- Список заменённых компонентов с привязкой к справочнику.
- Автоматическое списание со склада.
- Себестоимость использованных деталей.

**Стартовый промпт для диагностики:**

При создании нового ремонта инженер заполняет структурированный шаблон:
- Тип устройства, модель, платформа.
- Симптомы (из перечня + свободное поле).
- Что уже сделано.
- Наличие оборудования (мультиметр, осциллограф, ЛБП, тепловизор и т.д.).
- Первичные измерения.
- Наличие схемы/boardview.

Этот контекст автоматически передаётся в LLM при первом запросе.

### 2.4. Экспертная система диагностики с LLM

**Режим «Следующий шаг»:**

На основе текущих данных ремонта система формирует структурированный запрос к LLM и отображает:
- Список вероятных причин с оценкой вероятности (%).
- Рекомендуемое следующее измерение (где, чем, что должно быть).
- Ссылки на похожие ремонты из базы (через RAG).
- Ссылки на релевантные даташиты.

**Режим «Младший инженер» (пошаговый мастер):**

Для начинающих или незнакомых платформ — интерактивный диагностический мастер:
- Система задаёт вопросы по порядку (VIN → дежурки → мультиконтроллер → ...).
- После каждого ответа корректирует гипотезы.
- Отображает последовательность: VIN → Защита → Дежурные напряжения → Мультиконтроллер → Кнопка → S5 → S3 → S0 → VRM CPU → Инициализация.

**Контекстный чат с LLM:**

Произвольный диалог с привязкой к текущему тикету. Контекст формируется автоматически:
```json
{
  "device": "Lenovo ThinkPad T14 Gen2",
  "board": "NM-D221",
  "symptom": "Не включается",
  "measurements": { "VIN": 19.4, "3VALW": 3.3, "5VALW": 0.0 },
  "history": ["Проверены входные MOSFET", "Проверена цепь питания EC"],
  "similar_repairs": [125, 332, 911]
}
```

**Поддерживаемые LLM-провайдеры (через единый адаптер):**
- Grok / xAI API
- OpenAI API (GPT-4o и выше)
- Anthropic API (Claude)
- Ollama (локальные модели: LLaMA, Mistral, Qwen и т.д.)
- OpenRouter
- LM Studio
- llama.cpp-совместимые серверы
- vLLM

Переключение провайдера без перезапуска приложения. Возможность задать разные модели для диагностики и для генерации документов.

### 2.5. RAG — Поиск по базе знаний

**Четыре отдельных векторных индекса:**

| Индекс              | Содержание                                       |
|---------------------|--------------------------------------------------|
| `repair_vectors`    | Закрытые ремонты мастерской                      |
| `datasheet_vectors` | Даташиты компонентов (чанки по 512 токенов)      |
| `forum_vectors`     | Импортированные форумные решения (опционально)   |
| `knowledge_vectors` | Заметки инженеров, мануалы, внутренние статьи    |

**Пайплайн индексации:**
```
Новый PDF-даташит → OCR (Tesseract) → Разбивка на чанки → Embedding → Qdrant
Закрытый ремонт   → Формирование текста → Embedding → Qdrant
```

**Хранение:** текст хранится в MariaDB, в Qdrant хранятся только вектора и `object_id` для обратной ссылки. Это упрощает бэкап и миграции.

**Семантический поиск:** пользователь вводит запрос на естественном языке («ноутбук включается и сразу выключается»), система находит похожие ремонты и статьи.

### 2.6. База знаний

- Статьи и заметки мастеров (редактор в Markdown).
- Типовые неисправности по моделям и платформам.
- Шаблоны диагностических чек-листов (ноутбуки, БП, смартфоны, материнские платы).
- Схемы, boardview, сервис-мануалы с привязкой к моделям устройств.
- Форумные решения (ручной импорт или парсер).
- Полнотекстовый + семантический поиск.
- Тегирование и категоризация.

---

### 2.7. База компонентов

**Карточка компонента:**
- Наименование, артикул (part number), производитель.
- Тип (MOSFET, конденсатор, PMIC, ШИМ-контроллер, диод, резистор и т.д.).
- Корпус (TO-220, QFN32, 0603 и т.д.).
- Электрические параметры (напряжение, ток, сопротивление и т.д.).
- Ссылка на даташит (хранится в файловом хранилище).
- Список аналогов с указанием степени совместимости.

**Граф связей:**
- Компонент ↔ Ремонты, где он использовался.
- Компонент ↔ Устройства/платформы, где встречается.
- Компонент ↔ Даташиты.

**Статистика по компоненту:**
- Сколько раз заменялся.
- Процент успешных ремонтов после замены.
- В каких устройствах чаще всего выходит из строя.

**Автоматический поиск аналогов:**

При отсутствии нужного компонента — поиск замены с совпадением параметров и корпуса.

### 2.8. База платформ ноутбуков

- Каталог плат: LA-XXXX, NM-XXXX, DA0XXXX и т.д.
- Привязка схем и boardview к платформе.
- Типовые точки измерения и нормы напряжений.
- Статистика неисправностей по платформе.
- Тепловая карта неисправностей (визуализация поверх boardview, если доступен).

- Автосписание компонентов при закрытии ремонта.
- Минимальный остаток и уведомление о пополнении.
- Место хранения (полка, ячейка, ящик).

**Поставщики:**

- Каталог компонентов от поставщика с ценами.

- Сравнение цен на один компонент у разных поставщиков.

### 2.11. Документооборот

**Генерируемые документы (PDF):**

| Документ                    | Когда                              |
|-----------------------------|------------------------------------|
| Квитанция о приёмке         | При создании тикета                |
| Акт приёмки-передачи        | При создании тикета                |

- Шаблоны на базе Jinja2 (HTML → PDF через WeasyPrint).
- Логотип и реквизиты мастерской настраиваются в параметрах.
- Печать напрямую из приложения.
- Хранение сгенерированных документов в файловом хранилище.
- QR-код тикета на всех документах для быстрого доступа.

### 2.12. Файловое хранилище

**Структура хранилища:**
```
storage/
├── clients/{client_id}/
├── repairs/{ticket_id}/
│   ├── photos/           ← фото при приёмке и в процессе ремонта
│   ├── oscillograms/     ← осциллограммы
```

- Автоматический OCR новых PDF-даташитов и индексация в Qdrant.

## 3. Нефункциональные требования

### 3.1. Технический стек

| Компонент            | Технология                                                          |
|----------------------|---------------------------------------------------------------------|
| Язык                 | Python 3.11+                                                        |
| GUI                  | PySide6 (Qt6)                                                       |
| Бэкенд               | FastAPI (REST API, запускается как дочерний процесс)               |
| Основная СУБД        | MariaDB 10.11+ / 11.x (InnoDB, utf8mb4)                            |
| Векторная СУБД       | Qdrant                                                              |
| ORM                  | SQLAlchemy 2.x + Alembic (миграции)                                |
| LLM-фреймворк        | LangChain / LlamaIndex (через единый адаптер)                      |
| Генерация PDF        | WeasyPrint + Jinja2                                                 |
| OCR                  | Tesseract 5+                                                        |
| Эмбеддинги           | BGE-M3 или nomic-embed-text (локально через Ollama)                |
| Файловое хранилище   | Локальная ФС (+ опциональный MinIO для сетевых инсталляций)        |
| Контейнеризация      | Docker Compose (MariaDB + Qdrant + MinIO как сервисы)              |

### 3.2. Платформы

- Windows 10/11 (основная платформа).
- Linux (Ubuntu 22.04+, Debian 12+).
- Установщик для Windows (NSIS или MSI).

### 3.3. Производительность

- Поиск по 100 000+ записям ремонтов — до 1 секунды.
- Семантический поиск по 500 000 чанкам — до 2 секунд.
- Генерация PDF-документа — до 3 секунд.
- Открытие карточки тикета — до 0.5 секунды.
- Работа с 100 000+ файлами в хранилище без потери производительности.

### 3.4. Безопасность

- Пароли пользователей хранятся в виде bcrypt-хэшей.
- Пароли устройств клиентов шифруются (AES-256).
- Разграничение прав доступа по ролям на уровне API.
- Журнал аудита: все действия пользователей с меткой времени.
- HTTPS для внутреннего API (самоподписанный сертификат).

### 3.5. Надёжность

- Транзакционная целостность в MariaDB (InnoDB).
- Автоматический бэкап по расписанию.
- Graceful shutdown с сохранением незафиксированных данных.
- Логирование ошибок в файл с ротацией.

### 3.6. Оффлайн-режим

Система должна полностью функционировать без подключения к интернету, за исключением вызовов к облачным LLM. Локальные модели через Ollama обеспечивают полный оффлайн-режим AI.

## 6. Этапы разработки

### Этап 1 — Ядро и инфраструктура (2–3 месяца)
- Проектирование и создание схемы БД.
- Docker Compose: MariaDB + Qdrant.
- FastAPI backend: базовая структура, аутентификация, роли.
- PySide6 каркас: главное окно, авторизация, навигация.
- Alembic: система миграций.

### Этап 2 — CRM и приёмка (1–2 месяца)
- Модуль клиентов.
- Модуль устройств.
- Модуль тикетов: создание, статусы, поиск.
- Генерация PDF: квитанции, акты приёмки.

### Этап 3 — Ремонт и компоненты (2 месяца)
- Журнал ремонта.
- Карта измерений.
- База компонентов.
- Склад и списание.
- Файловое хранилище и вложения.

### Этап 4 — LLM и RAG (2–3 месяца)
- LLM Adapter (Ollama / OpenAI / Grok / Claude).
- Пайплайн индексации (OCR → чанки → эмбеддинги → Qdrant).
- Режим «Следующий шаг».
- Режим «Младший инженер».
- RAG-поиск по ремонтам и даташитам.

### Этап 5 — Финансы и документооборот (1–2 месяца)
- Финансовый модуль.
- Поставщики.
- Полный цикл документов.

### Этап 6 — Аналитика и шлифовка (1 месяц)
- Дашборды и отчёты.
- Уведомления и напоминания.
- Экспорт/импорт данных.
- Резервное копирование.
- Тестирование, багфиксинг, UI/UX полировка.

## 8. Перспективы развития (версия 2.0+)

- Визуальная карта платы: кликабельный boardview с историей ремонтов по компонентам.
- Тепловая карта неисправностей поверх boardview на основе статистики ремонтов.
- Мобильное приложение для приёмщика (просмотр статусов, уведомления).
- Интеграция с онлайн-магазинами запчастей (Mouser, DigiKey, LCSC) для сравнения цен.
- Тонкая настройка (fine-tuning) локальной модели на собственной базе ремонтов.
- Многофилиальный режим с централизованной БД.
- Голосовой ввод измерений и заметок.
- Поддержка планшета с цифровым пером для аннотаций схем.
